# Security model

The Dashboard investigations application performs bounded read-only Wazuh searches and agent/SCA reads. The model receives only server-selected evidence snapshots; no Wazuh write tool exists. Production mode requires a 32-character server-only proxy token and an authenticated user identifier. The HTTP service refuses non-loopback binding. The browser preview is available only in explicit demo mode. Sessions and investigations are keyed by owner in every read and write query. Model responses are rendered as text, not HTML.

The provider adapter accepts only a configured approved hostname and `/v1` path, uses TLS by default, rejects metadata and forbidden address classes, resolves to one address, and pins the socket to that address while retaining certificate validation against the hostname. Plain HTTP is limited to explicit loopback test mode. The provider key is accepted from an administrator over the authenticated Dashboard route and stored in a private mode 0600 server file. It is omitted from errors and logs and never returned by the API. The proxy and admin tokens stay in protected service environment files.

Limits: 24 KiB request bodies, 4,000-character user messages, 6,000-character investigation evidence, 20 conversation turns sent to the model, 16,000-character answers, 4 MiB provider streams, 100 discovered models, and 180-second maximum provider timeout. The model has no callable tools yet. Failure never triggers a cloud fallback.

The native plugin requires a configured indexer admin role (default `all_access`) and a separate server-only admin token for provider changes. Retention and deletion are limited to the current user’s owner ID. Expired sessions are pruned on save and hourly. The native plugin derives identity using the indexer's current-user `authinfo` endpoint, hashes the username and requested tenant into an owner ID, sends a server-only token to the loopback service, and supplies the Dashboard XSRF header from the browser. Indexer searches use `asCurrentUser`; Wazuh agent and SCA reads use Wazuh Core's scoped client. Read routes have fixed index/path allowlists, bounded time ranges, and result limits. Later model-directed tools need per-user authorization, audit trails, and stricter output validation. The privileged executor must be a separate process and deny all AI-originated changes until independently validated.

Known prototype limits: demo mode has no authentication; the SQLite database is not encrypted at rest; provider keys are held in a private local file rather than an external secrets manager; no audit ledger or rate limit is implemented yet. Do not expose this checkpoint to other users or feed it confidential Wazuh events.
