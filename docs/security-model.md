# Security model

The Dashboard investigations application and chat tool broker perform bounded read-only Wazuh searches and agent/SCA reads. The model may request only the defined read and capability tools; no Wazuh write tool exists. Production mode requires a 32-character server-only proxy token and an authenticated user identifier. The HTTP service refuses non-loopback binding. The preview is available only in explicit demo mode. Sessions and investigations are keyed by owner in every read and write query. Model responses are rendered as text, not HTML.

The provider adapter accepts only a configured approved hostname and `/v1` path, uses TLS by default, rejects metadata and forbidden address classes, resolves to one address, and pins the socket to that address while retaining certificate validation against the hostname. Plain HTTP is limited to explicit loopback test mode. The provider key is accepted from an administrator over the authenticated Dashboard route and stored in a private mode 0600 server file. It is omitted from errors and logs and never returned by the API. The proxy and admin tokens stay in protected service environment files.

Limits: 16,000-character user messages and assistant answers, 6,000-character investigation evidence, the 12 most recent history messages within a 24,000-character budget, 196,608-byte internal model requests, 4 MiB provider streams, 100 discovered models, and 180-second maximum provider timeout. Tool chat permits at most eight read calls over four tool rounds, with ten search results and a 12,000-character result cap. The final model request has a 4,096-token output budget; a provider `length` finish is rejected instead of saving a partial answer. Failure never triggers a cloud fallback.

The native plugin requires a configured indexer admin role (default `all_access`) and a separate server-only admin token for provider changes. Retention and deletion are limited to the current user’s owner ID. Expired sessions are pruned on save and hourly. The native plugin derives identity using the indexer's current-user `authinfo` endpoint, hashes the username and requested tenant into an owner ID, sends a server-only token to the loopback service, and supplies the Dashboard XSRF header from the client. Indexer searches use `asCurrentUser`; Wazuh agent and SCA reads use Wazuh Core's scoped client. The model cannot supply an arbitrary index, API path, search DSL, command, or destination. Each executed tool writes owner-scoped audit metadata without storing returned log bodies. The privileged executor must be a separate process and deny all AI-originated changes until independently validated.

Known limits: demo mode has no authentication or Wazuh tools; the SQLite database is not encrypted at rest; provider keys are held in a private local file rather than an external secrets manager; tool audit is metadata-only and there is no per-user rate limit yet. Restrict the Dashboard app to trusted operators, set chat retention deliberately, and review the model gateway's data handling before sending sensitive events to it.

Agent/SCA proposal validation requires the configured indexer admin role, a selected agent that belongs to the requested group, and a distinct server-only `ASSISTANT_POLICY_TOKEN`. The Dashboard sends only a fixed set of setting values to a loopback validator running as the Wazuh service account. The validator has no access to the live shared configuration write path; it stores valid proposals in a private directory and returns a complete diff and active-file SHA-256 hash. A separate apply service uses `ASSISTANT_POLICY_APPLY_TOKEN`, accepts only an owner-scoped saved proposal ID, rechecks the active hash and native syntax, and writes atomically after saving a private backup. It has a systemd write allowlist for Wazuh shared group configuration and its private policy directory. The Dashboard checks the administrator role and group membership before apply. Rollback requires the applied file hash to match. Neither service is callable by the model's read tools; agent distribution and SCA outcome remain separate checks.

Alert delivery uses a separate `ASSISTANT_ALERT_TOKEN` and a loopback service running as the Wazuh account. Only an indexer administrator can save a destination or trigger a synthetic test. Dashboard-only mode is the default. The webhook URL stays in a private SQLite database and is redacted from API responses. Each delivery re-resolves the hostname, enforces HTTPS and a single permitted IP, pins the TLS connection, and never follows redirects. The queue stores only bounded alert summaries. The current dispatcher has five retry attempts and no external dead-letter monitor; it should not be the sole path for guaranteed notifications.
